# 產品改版前先問這七件事：把個資處理變更管理做成真正的治理控制

很多個資風險不是新系統上線當天才出現，而是在一個看似很小的改動中慢慢形成。產品團隊新增一個推薦欄位，行銷團隊把客服紀錄接到分眾平台，客服系統換了新的外掛，財務流程把發票資料交給另一家雲端服務，或工程師為了讓模型回答得更完整，順手把整份會員紀錄放進檢索資料庫。

這些事情在專案管理上可能只是需求變更，在個資治理上卻可能代表蒐集目的改變、資料範圍擴大、接收對象增加、保存期限延長、跨境傳輸啟動，甚至讓原本低風險的流程變成需要重新評估的高風險處理活動。

企業若只在新專案開始時做一次個資盤點，之後就把所有風險交給年度稽核，通常會漏掉最多問題。因為資料處理不是靜態設計，而是會隨著產品、流程、供應商和商業模式持續變動。比較成熟的做法，是把個資處理變更管理納入既有的產品開發、採購、系統開發與發布流程，在變更發生前就判斷是否需要重新告知、重新評估、補充合約或調整控制。

本文提出一套適合台灣企業使用的變更管理方法。重點不是為每一個按鈕改色都安排法務審查，而是建立一個能分級、能留證、能追蹤例外的判斷機制。

## 一、什麼叫做個資處理變更

個資處理變更，不是只有新增一個資料庫或更換一套軟體。只要資料的來源、目的、類型、數量、使用方式、接收對象、保存期限、權限或處理地點發生足以影響風險的改變，就應該進入變更判斷。

可以先把變更分成八種類型：

| 變更類型 | 常見例子 | 可能引發的問題 |
| --- | --- | --- |
| 資料欄位變更 | 表單新增生日、職業、精確位置 | 是否仍屬必要範圍，告知是否完整 |
| 目的變更 | 從履約服務改成推薦或行銷分析 | 是否超出特定目的，是否需要新的法定依據 |
| 流程變更 | 客服紀錄改供模型摘要或品質評分 | 是否產生新的利用方式與當事人影響 |
| 對象變更 | 新增分析平台、外包客服或分包商 | 委外監督、提供告知與跨境問題 |
| 保存變更 | 報表保存由三個月改成三年 | 是否有保存理由，是否增加外洩暴露時間 |
| 地點變更 | 改用境外雲端區域或境外支援團隊 | 國際傳輸、供應商存取與契約控制 |
| 權限變更 | 更多部門可查詢完整會員紀錄 | 最小權限、目的限制與內部濫用風險 |
| 技術變更 | 導入 AI、指紋辨識或自動化決策 | 特種個資、高風險處理與可解釋性 |

這張表的用途不是把所有改動都升級成重大專案，而是提醒審查人員：產品需求單上的「新增欄位」和個資清冊上的「資料類別變更」，可能是同一件事的兩種描述。

《個人資料保護法》第 5 條要求個人資料的蒐集、處理及利用，不得逾越特定目的的必要範圍，並應與蒐集的目的具有正當合理的關聯。這個要求不只適用於第一次蒐集，也會影響後續把資料拿去做什麼。企業不能因為資料早已合法進入系統，就把所有新的用途都視為當然可以使用。[個人資料保護法](https://law.pdpc.gov.tw/LawContent.aspx?id=FL010627)

## 二、先建立變更觸發條件，不要等承辦人自己想起來

變更管理最常失效的原因，是制度寫著「重大變更應重新評估」，卻沒有定義什麼叫重大。最後每個部門都用自己的直覺判斷，產品團隊認為只是功能調整，資安團隊認為只是 API 變更，法務團隊則可能直到合約審查時才發現資料已經送到新的服務商。

企業可以把以下情況列為至少需要進行個資初篩的觸發條件：

- 新增或移除個人資料欄位。
- 將原本只供服務履行的資料，用於分析、推薦、訓練、行銷或員工評分。
- 新增外部服務商、分包商、模型服務、客服平台或資料交換介面。
- 資料處理地點從台灣改為境外，或新增境外人員支援權限。
- 將單一來源資料與其他資料集串接，形成更完整的個人輪廓。
- 將人工判斷改成自動化分級、推薦、拒絕或排序。
- 新增病歷、醫療、健康檢查、基因、性生活或犯罪前科等特種個資。
- 延長保存期限，或把原本會刪除的資料移入長期分析資料集。
- 讓更多內部角色查詢、匯出或下載原始個人資料。
- 發生資料事件、當事人申訴、主管機關要求或重大稽核缺失。

其中最後一項很容易被忽略。變更管理不是只有「要上線新功能時」才啟動。事件與申訴提供了實際運作證據，可能顯示原本的風險假設已經不成立，因此也應該觸發重新評估。

比較好的制度設計，是把這些觸發條件做成產品開發工具、採購申請單、系統變更單和供應商評估表中的必填問題，而不是只放在個資政策附件裡。

## 三、七個問題，先判斷變更要走哪一條路

每一次初篩不必一開始就要求提交數十頁報告。可以先用七個問題判斷變更的性質，再決定需要哪些審查。

### 1. 資料有沒有變多，或變得更容易識別

資料量增加當然會提高暴露面，但資料種類的變化有時更重要。原本只有訂單編號的報表，若新增姓名、電話、地址和購買紀錄，就可能從低識別性資料變成可以直接接觸當事人的完整資料集。

也要注意資料組合後的識別能力。個別欄位看起來都不敏感，不代表合在一起沒有風險。出生年月、郵遞區號、職業和消費時間，可能已足以讓內部人員鎖定特定客戶。若資料要進入分析平台或模型索引，審查時應看實際可查詢的組合，而不是只看資料字典中的欄位名稱。

### 2. 原本的目的是否仍然相同

「同一套系統」不代表「同一個目的」。會員資料原本用於登入與訂單服務，後來拿來預測流失；客服對話原本用於處理客訴，後來拿來訓練品質模型；員工出勤資料原本用於薪資計算，後來拿來建立績效排名。這些用途都可能有業務上的合理性，但合理性不能取代目的與必要性的判斷。

審查表不應只讓申請人勾選「既有目的」。應要求申請人用一句完整的話寫出處理目的，例如「依會員最近六個月的購買紀錄產生補貨提醒」，而不是寫「提升行銷效率」。目的越具體，後續才越能判斷欄位、權限、保存期限與輸出對象是否適當。

### 3. 新用途是否需要重新告知或取得同意

企業不能把「隱私權政策已經寫得很廣」當成萬用通行證。告知內容雖然可以描述多種處理情境，但仍應讓當事人理解資料會被如何使用、由誰處理、提供給哪些對象，以及可能帶來什麼影響。文字寫得很寬，不一定就能支持所有未來用途。

如果新用途涉及行銷、精確位置、特種個資、自動化決策、跨境傳輸或對當事人有顯著影響的分類，應提高審查層級。這不代表每一種情況都必然需要重新取得同意，而是要把適用的法定事由、告知內容、拒絕或撤回機制說清楚，不要讓技術團隊自行推定。

### 4. 誰會接觸資料，供應商角色有沒有改變

新服務商不一定只是工具供應商。要先確認它是否會替企業蒐集、處理或利用個人資料，是否會再交給其他服務商，是否會讓境外人員查閱，以及服務終止後如何返還、刪除或處理備份。

《個人資料保護法施行細則》第 8 條列出委託監督應注意的內容，包括委託範圍、個人資料類別、特定目的、期間、安全措施、複委託、事故通知與補救，以及契約終止時的返還與刪除等。這些內容不應只由法務寫進合約，還要能在系統與作業紀錄中驗證。否則契約上寫著禁止分包，實際上卻不知道模型服務、雲端託管和內容安全服務各自位於哪一層。[個人資料保護法施行細則](https://law.pdpc.gov.tw/LawContent.aspx?id=FL010628)

### 5. 保存終點有沒有被往後推

產品改版很容易產生「先留著，以後可能有用」的資料。分析團隊會要求保留原始事件，客服會要求保留完整對話，工程團隊會要求保留所有 log，最後不同資料集都沒有明確的刪除責任人。

每一項變更都應重新回答三個問題：資料為何要保存？保存多久？到期後是刪除、匿名化、停止利用還是移到限制存取的封存區？《個人資料保護法》第 11 條要求特定目的消失或期限屆滿時，應刪除、停止處理或停止利用，但因執行職務或業務所必須，或經當事人書面同意者，不在此限。保存期限的改變應留下理由，不應只在資料庫欄位填上「永久」。

### 6. 當事人的風險是否上升

同樣一批資料，處理方式不同，對當事人的影響可能完全不同。把資料放在限定客服人員查詢的系統，和把資料交給自動化模型產生信用風險標籤，不能用同一個風險等級處理。

初篩至少要看：

- 是否涉及脆弱族群，例如兒少、病患、身心障礙者或遭受暴力者。
- 是否可能影響服務資格、價格、工作機會、信用、保險或其他重要決定。
- 是否會產生新的個人輪廓、推論或敏感分類。
- 當事人能否知道、理解、糾正或申訴處理結果。
- 出錯後能否回復，還是會留下長期且難以逆轉的影響。

台灣現行法規對每一種產品變更未必都提供一套完整的量表，但這不表示企業可以不評估。個資保護法施行細則已將個人資料風險評估及管理機制列為安全維護措施的一部分。企業應建立自己的判斷因子與紀錄方式，讓不同專案的判斷可以比較，也讓日後的稽核與事件調查有依據。

### 7. 變更後如何證明控制真的生效

許多審查停在「需求已核准、合約已簽署、隱私政策已更新」，卻沒有確認系統是否依核准內容運作。變更完成後至少要驗證：

- 實際傳送的欄位是否和核准範圍相同。
- 新增的資料接收者是否真的受到權限與合約限制。
- 告知版本、同意狀態與資料處理目的是否能互相對照。
- 保存與刪除排程是否已啟用，且有成功與失敗紀錄。
- 撤回、拒絕、刪除或更正要求能否傳到所有下游系統。
- 監控、稽核 log 和例外告警是否能支持事後查核。

沒有驗證的核准，只是文件流程；沒有回讀的控制，不能證明風險真的降低。

## 四、把變更分成四級，避免審查制度被繞過

如果每一項變更都要求相同程序，業務會覺得個資治理只會拖慢交付，最後反而出現私下開帳號、繞過採購或先上線再補文件的情況。分級的目的，是把有限的審查資源用在真正可能改變風險的地方。

| 等級 | 判斷特徵 | 最低控制要求 |
| --- | --- | --- |
| 第一級：例行 | 不新增資料、不改目的、不改接收者，只調整畫面或技術實作 | 由產品或系統負責人自我檢核並留紀錄 |
| 第二級：受控 | 新增一般個資欄位、權限或保存設定，但目的與處理地點未變 | 個資窗口檢視必要性、告知、清冊與測試證據 |
| 第三級：重大 | 新用途、新供應商、跨境、資料串接、長期保存或大量資料 | 個資、法務、資安與業務共同審查，必要時更新合約與風險評估 |
| 第四級：高風險 | 特種個資、大規模監控、自動化重要決策、脆弱族群或重大當事人影響 | 上線前完成影響評估、管理階層核准、控制測試與上線後回顧 |

分級不是為了替企業宣稱哪一級一定合法，而是決定需要哪些程序和證據。每個等級都要允許升級。例如，原本判定為第二級的欄位新增，如果後來發現資料會送到境外模型，就應重新升級，而不是沿用最初的低風險結論。

## 五、變更申請單應該記錄什麼

一份實用的變更申請單，不需要把法律意見全文貼進去，但要能讓沒有參與原始設計的人理解決策脈絡。建議至少包含以下欄位：

| 欄位 | 記錄內容 |
| --- | --- |
| 變更名稱與版本 | 讓後續能對應產品 release、工單與程式版本 |
| 業務目的 | 用具體動作描述，不使用「提升效率」等空泛用語 |
| 受影響資料 | 資料類別、來源、是否含特種個資、預估筆數 |
| 處理流程 | 從蒐集、傳送、分析、輸出到刪除的流程圖或文字描述 |
| 接收對象 | 內部單位、受託者、分包商、境外人員與平台所在地 |
| 法定事由與告知 | 使用的法律依據、告知版本、是否需要重新取得同意 |
| 保存與刪除 | 起算點、期限、到期動作、備份處理方式 |
| 當事人影響 | 可能的利益、權利與自由影響，以及降低措施 |
| 控制措施 | 權限、遮罩、加密、記錄、人工覆核與例外處理 |
| 測試證據 | 測試案例、抽樣結果、失敗紀錄與修正結果 |
| 核准與例外 | 核准人、核准日期、未完成事項、補正期限 |
| 上線後檢視 | 指標、事件、申訴與重新評估觸發條件 |

「法定事由與告知」這一欄不能由系統開發人員自行填寫，也不能由法務只勾選「已確認」。比較好的做法，是讓申請人先描述實際流程，再由個資或法務人員確認判斷是否與資料流一致。

## 六、三個常見失敗案例

### 案例一：客服摘要功能變成新用途

假設某企業原本讓客服人員查閱客戶來電內容，以處理服務問題。產品團隊導入 AI 摘要後，把所有對話傳到外部模型，並保留模型輸入與輸出九十天，供日後改善提示詞。

這個需求至少包含四個變更：資料新增接收者、處理方式改變、保存期限延長，以及可能的跨境傳輸。若對話中含有健康、財務或家庭狀況，風險還會再上升。不能只因為摘要結果沒有直接顯示給客戶，就認定影響很小。

較穩妥的控制包括：先限制模型取得的欄位，移除與摘要無關的識別資訊；確認模型服務商是否使用輸入資料進行訓練；區分正式服務紀錄與改善用途的測試資料；縮短原始輸入保存期限；讓客服主管可以人工覆核高風險摘要；並以抽樣方式比對模型實際送出的內容和核准範圍。

### 案例二：行銷平台要求完整會員資料

假設行銷部門要建立會員分眾，平台商要求上傳姓名、電子郵件、電話、地址、生日、交易紀錄與客服標籤。申請單只寫「提升行銷精準度」。

這份申請不能直接核准，因為資料欄位、目的、必要性與保存期限都還沒有說清楚。應要求申請人說明每個欄位如何影響分群結果，是否可以使用雜湊識別碼或區間資料取代直接識別資料，哪些客服標籤可能含有敏感內容，以及取消行銷後資料如何從平台移除。

如果平台商還會把資料交給廣告投放夥伴，企業就要重新判斷對象、告知與委外控制。把所有資料打包後再交給供應商，不是分眾精準的充分理由。

### 案例三：離職員工資料改供人力分析

假設人資原本保存離職資料，用於薪資、勞健保與爭議處理。管理階層希望把離職原因、績效、薪資和主管評語整合，找出高離職風險部門。

這項改動不只是多一張報表，而是把人事資料轉成員工分析與管理工具。審查時要確認分析結果是否會影響升遷、調薪或續約，誰能查閱個人層級結果，是否真的需要保留姓名，模型或規則是否會對特定群體產生不公平影響，以及員工能否知道資料被如何利用。

若分析只需要部門和月份層級的趨勢，就不應直接建立可以追溯到個人的排名。資料越接近決策現場，越需要限制用途、縮小資料粒度並保留人工判斷責任。

## 七、例外情況怎麼處理，才不會變成永久繞道

實務上一定會遇到不能等完整審查才上線的情況，例如重大資安事件、法令期限、客戶服務中斷或供應商緊急替換。企業可以設計快速通道，但快速通道不能等於免審查。

例外流程至少要包含：

- 說明為什麼無法走一般流程，以及不處理會造成什麼風險。
- 指定臨時核准人，不由提出需求的人單獨核准。
- 定義臨時資料範圍、有效期限與停止條件。
- 先採取最低必要的資料、權限與保存設定。
- 設定補正期限，逾期自動升級給管理階層。
- 在事後完成正式評估、合約、告知與控制測試。
- 記錄例外期間發生的事件、申訴和實際資料流。

最危險的例外，不是有一張緊急申請單，而是緊急設定從未被關閉。企業應每月或每季列出仍在使用的臨時權限、臨時資料交換與未完成補正事項，要求負責人重新確認是否仍有必要。

## 八、怎麼衡量變更管理有沒有用

如果只統計完成多少份申請單，容易鼓勵形式合規。比較有用的指標，應該反映判斷品質和控制結果：

- 新產品或重大變更中，完成個資初篩的比例。
- 從需求提出到完成初篩的中位天數。
- 被升級到第三級或第四級的變更比例。
- 上線後才發現未申報個資變更的件數。
- 變更後告知、合約、資料清冊與權限設定的更新完成率。
- 下游供應商撤回、刪除或停止處理要求的完成時間。
- 例外流程逾期未補正的件數。
- 控制測試發現的重複性缺失與改善完成率。
- 變更上線後三十至九十天內的申訴、事件或錯誤使用紀錄。

其中「未申報變更件數」不應被拿來單純懲罰部門，否則大家只會把問題藏起來。更好的用法，是把它當成流程感測器：如果某個團隊反覆在上線後才補申請，可能代表觸發條件不清楚、工具沒有嵌入工作流程，或審查時程與產品交付節奏不匹配。

## 九、導入順序：先做最小可行控制，再逐步擴大

沒有變更管理制度的企業，不必一開始就建立全公司最複雜的審查委員會。可以按照以下順序導入：

### 第一步：盤點高頻變更入口

先找出產品 release、採購申請、系統變更、資料交換、行銷活動與 AI 專案等主要入口。每個入口只增加三到七個初篩問題，確認新增資料、目的、對象、地點、保存和當事人影響。

### 第二步：建立一頁式分級規則

把四級判斷寫成業務人員看得懂的問題，不要只引用法規條文。規則要說明哪些情況可以自我檢核，哪些情況必須找個資、法務或資安人員，哪些情況需要管理階層核准。

### 第三步：把清冊與工單連起來

不要讓產品工單、供應商清冊、資料處理活動清冊和風險評估各自存在。至少要用同一個變更編號串起需求、核准、測試、版本、合約與上線後回顧，才能在事件發生時迅速還原決策。

### 第四步：挑三個真實專案做回溯測試

找最近已上線的三個功能，反向檢查當時的資料範圍、告知、權限、保存和供應商設定。這通常比先寫一份很長的政策更容易發現制度缺口。

### 第五步：把未申報變更納入稽核與管理報告

定期比較程式碼版本、API 權限、雲端帳號、資料庫欄位、供應商清冊和個資清冊，找出未經審查的資料流。發現差異後，不要只要求補文件，也要追查為什麼原本的流程沒有攔住它。

## 十、最後的檢核表

產品或流程準備上線前，可以用以下問題做最後確認：

- 這次變更是否新增、移除或重新組合個人資料欄位？
- 實際目的是否和原本告知的目的相同？
- 是否使用了「提升效率」「最佳化體驗」等無法測試的目的描述？
- 是否新增外部服務商、分包商、模型、分析平台或境外人員？
- 是否確認供應商不會把資料用於未核准的訓練、分析或廣告用途？
- 是否重新檢查資料處理地點、跨境傳輸與存取權限？
- 是否重新確認保存期限、備份、測試環境與匯出檔的刪除方式？
- 是否涉及特種個資、脆弱族群或可能影響重要權益的自動化處理？
- 當事人是否有合理方式知道、拒絕、更正、刪除或提出申訴？
- 審查結論是否有具體理由，而不是只勾選低風險？
- 上線後是否安排控制測試、指標監控與重新評估條件？
- 如果走例外流程，是否有明確期限和補正責任人？

## 結論：把個資審查放進變更流程，而不是放在流程外面

個資治理最怕兩種極端。一種是所有事情都要等一份很長的法律審查，最後業務為了交付而繞過制度；另一種是把所有變更都當成技術問題，等發生事件後才發現資料目的、接收對象和保存期限早已改變。

可行的中間道路，是把個資處理變更管理做成日常流程的一部分。先用明確觸發條件抓出需要判斷的變更，再依資料、目的、對象、地點、保存與當事人影響分級。低風險變更快速通過，高風險變更留下完整決策與測試證據，例外變更則必須有期限、責任人和事後回補。

企業真正要建立的，不是一道阻擋產品交付的審查關卡，而是一套能讓人及早看見資料處理改變、在風險還能調整時做出選擇的控制。當每一次重要改版都能回答「改了什麼、為什麼可以改、誰會受到影響、上線後如何證明仍在控制內」，個資治理才算真正進入營運，而不是只留在政策和稽核資料夾裡。
